# Chat Message Storage & Pagination (การจัดเก็บและเรียกดูประวัติข้อความ)

---

## ปฐมนิเทศ (Orient)

ในระบบแชท ข้อมูลข้อความเป็นสิ่งที่เพิ่มขึ้นมหาศาลอย่างรวดเร็ว (WhatsApp มีข้อความไหลผ่านกว่า 1 แสนล้านข้อความต่อวัน) การใช้คำสั่ง SQL พื้นฐานเพื่อดึงข้อมูลจะกลายเป็นหายนะเมื่อฐานข้อมูลของคุณโตขึ้น บทเรียนนี้จะสอนกลยุทธ์การจัดเก็บข้อมูลแบบ **Hot/Warm/Cold **, การทำ **Time-based Partitioning ** และทำไม **Cursor-based Pagination ** ถึงเป็นฮีโร่ที่มาแทนที่ OFFSET

---

## ลองทำก่อน (Attempt)

> ** สถานการณ์:** คุณมีตาราง`messages` ที่มีข้อมูล 1 พันล้านแถว ผู้ใช้ต้องการ"เลื่อนดูข้อความเก่า" เมื่อ 2 เดือนที่แล้ว
>
> ** คำถาม:** หากคุณใช้ Query แบบนี้:
>`SELECT * FROM messages WHERE conversation_id = 123 ORDER BY created_at DESC LIMIT 50 OFFSET 1000000`
> ทำไมคำสั่งนี้ถึงถือเป็น"บาป" ในการออกแบบระบบระดับ Senior? และมันจะส่งผลอย่างไรต่อฐานข้อมูลของคุณ?
>
> **✋ หยุดตรงนี้ก่อน **— ลองคิดสัก 30 วินาที (คำใบ้: ลองนึกถึงสิ่งที่ Database 📦 ต้องทำเมื่อเจอคำว่า OFFSET ดูสิ)

## ผลตอบรับ (Feedback)

| หากคุณตอบว่า... | การวิเคราะห์ |
|:---|:---|
|"แค่เพิ่ม Index ก็เร็วแล้ว" | ❌ ** ไม่ช่วย!** แม้จะมี Index แต่ Database 📦 ยังต้องทำการ"อ่านและข้าม" (Read & Skip) 1 ล้านแถวแรกทิ้งไปก่อนจะเอา 50 แถวที่ต้องการ |
|"ใช้ Cursor-based Pagination" | ✅ ** ถูกต้อง!** เราจะใช้ค่าของแถวสุดท้าย (เช่น Timestamp หรือ ID) มาเป็นจุดเริ่มแทนการนับจำนวน (OFFSET) |
|"Cursor + Data Partitioning" | ✅ **Senior-level!** คุณเข้าใจทั้งการเพิ่มความเร็วในการ Query และการบริหารจัดการขนาดของไฟล์ข้อมูลทางกายภาพ |

**หัวใจสำคัญ:**OFFSET มีความซับซ้อนระดับ **O(N)** ยิ่งข้อมูลเยอะยิ่งช้า แต่ Cursor มีความซับซ้อนระดับ **O(log N)** ซึ่งเร็วคงที่เสมอไม่ว่าข้อมูลจะมากแค่ไหน

### คำอธิบาย (Explain)

การเลือกฐานข้อมูลสำหรับเก็บข้อความแชทต้องคำนึงถึงความสามารถในการเขียนที่รวดเร็ว (Write-heavy) และการทำ Pagination ที่มีประสิทธิภาพสูงในระดับพันล้านแถว [source: Discord Engineering — How Discord Stores Billions of Messages]

### 1. Cursor-based Pagination: วิธีที่ถูกต้อง

แทนที่จะบอกว่า"ข้ามไป 1 ล้านแถว" เราจะบอกว่า **"เอาข้อความ 50 อันถัดไปที่เก่ากว่าข้อความ ID: 1000000"**:
```sql
-- วิธีที่เร็วกว่ามหาศาล
SELECT * FROM messages
WHERE conversation_id = 123 AND message_id < 1000000
ORDER BY message_id DESC
LIMIT 50;
```
Database 📦 จะใช้ความสามารถของ B-Tree Index กระโดดไปยังตำแหน่ง ID: 1000000 ทันทีและดึง 50 แถวออกมาโดยไม่ต้อง"ข้าม" อะไรเลย

### 2. Tiered Storage (Hot, Warm, Cold)
เราไม่ควรเก็บข้อความทุกอย่างไว้ในที่ที่แพงที่สุด:
-   **Hot (Redis):** ข้อความใน 7 วันล่าสุด (เข้าถึงบ่อยที่สุด เร็วที่สุด)
-  **Warm (MongoDB/Postgres):** ข้อความย้อนหลัง 1-6 เดือน (เก็บใน Disk ที่เร็วระดับหนึ่ง)
-  **Cold (S3/GCS):** ข้อความเก่ากว่า 6 เดือน (บีบอัดและเก็บในที่ที่ราคาถูกที่สุด เพื่อลด Cost)

### 3. Time-based Partitioning
แทนที่จะมี 1 ตารางยักษ์ที่มี 1 พันล้านแถว เราจะแบ่งตารางตามเดือน:
-  `messages_2026_04`
-  `messages_2026_05`
เมื่อเราค้นหาข้อความเดือนเมษายน Database 📦 จะพุ่งตรงไปที่ตารางเมษายนตารางเดียว และข้ามตารางอื่นๆ ไปทั้งหมด (Partition Pruning)

## ขยายความ (Extend)

### การจัดการไฟล์แนบ (Media Storage Strategy)
ห้ามเก็บรูปภาพหรือวิดีโอ (Binary Data) ลงใน Database 📦 โดยตรงเด็ดขาด!
-  **วิธีที่ถูก:** อัปโหลดไฟล์ไปที่ **Object Storage **(เช่น AWS S3 หรือ Google Cloud Storage) แล้วเก็บเพียง **URL ** และ Metadata (ขนาดไฟล์, ประเภทไฟล์) ลงในฐานข้อมูล
-  **CDN:** ใช้ Content Delivery Network 📡 เพื่อให้ผู้ใช้โหลดรูปภาพจาก Server ที่อยู่ใกล้ตัวเขาที่สุด

### กรณีศึกษา: สถาปัตยกรรมจัดเก็บข้อมูลระบบแชทจริง
ในสถาปัตยกรรมตัวอย่าง:
-  **MongoDB ** คือ Warm Storage หลักที่เราใช้เก็บข้อความ เพราะรองรับการขยายตัว (Sharding) ได้ง่าย
-  **Cursor Pagination:** ทุก API ที่ดึงประวัติแชทจะบังคับใช้ Cursor เสมอ
-  **Attachment Logic:** เมื่อลูกค้าส่งรูปผ่าน LINE/Facebook ระบบจะโหลดรูปมาฝากไว้ที่ Google Cloud Storage ก่อน แล้วค่อยส่ง URL ให้เจ้าหน้าที่ดู เพื่อความเร็วและความมั่นคงของข้อมูล

## จุดตรวจสอบ (Checkpoint)

> **Quick Check:**
> 1. ทำไม OFFSET 1,000,000 ถึงทำให้ Database 📦 ทำงานหนัก?
> 2. ประโยชน์ของการทำ Table Partitioning คืออะไร?
> 3. หากต้องการดึงข้อความ"ถัดไป" ใน Cursor Pagination เราต้องส่งค่าอะไรกลับไปให้ Client?

<details>
<summary>คลิกเพื่อดูคำตอบ</summary>

1. เพราะ Database 📦 ต้อง Scan และ Sort ข้อมูล 1 ล้านแถวนั้นเพื่อหาจุดเริ่มต้น แม้ว่าสุดท้ายจะไม่ได้ใช้ข้อมูลเหล่านั้นเลยก็ตาม
2. ช่วยลดปริมาณข้อมูลที่ Database 📦 ต้อง Scan (Search Space) และทำให้การทำ Maintenance (เช่น ลบข้อมูลเก่าทิ้ง) ทำได้ง่ายและเร็วขึ้น
3. ต้องส่ง **ID หรือ Timestamp ** ของข้อความ"สุดท้าย" ในหน้าปัจจุบัน เพื่อให้ Client ใช้เป็นจุดเริ่มต้นในคำขอหน้าถัดไป

</details>
