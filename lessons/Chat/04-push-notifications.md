# Push Notifications Design (ยุทธศาสตร์การออกแบบระบบแจ้งเตือน)

---

## ปฐมนิเทศ (Orient)

Push Notification ไม่ใช่แค่การเรียกใช้ FCM API แล้วจบงาน แต่มันคือการตัดสินใจที่ซับซ้อน: *เมื่อไหร่* ควรส่ง, *เมื่อไหร่* ควรเงียบ, และทำอย่างไรไม่ให้ผู้ใช้รำคาญจนลบแอปทิ้ง บทเรียนนี้จะพาคุณไปดูเบื้องหลังการทำงานของระบบ Push ในระดับที่ WhatsApp หรือ LINE ใช้งานจริง เพื่อสร้างสมดุลระหว่าง"ความรวดเร็ว" และ"ความพึงพอใจของผู้ใช้"

---

## ลองทำก่อน (Attempt)

> **สถานการณ์:** คุณส่งข้อความหาเพื่อนว่า"หิวข้าวยัง?"
> ** เงื่อนไข:**
> -   เพื่อนของคุณกำลัง ** เปิดแอป ** และดูหน้าแชทกับคุณอยู่ (Online & Active)
> -   ระบบของคุณตรวจพบว่าเพื่อนได้รับข้อความผ่าน WebSocket 📡 แล้ว
>
> ** คำถาม:** ในสถานการณ์นี้ คุณควรส่ง Push 📱 Notification 📱 ไปยังมือถือของเพื่อนอีกครั้งหรือไม่? เพราะเหตุใด?
>
> **✋ หยุดตรงนี้ก่อน **— ลองนึกถึงประสบการณ์ของคุณเวลาที่มือถือสั่นรัวๆ ทั้งที่มองหน้าจออยู่ดูสิ

---

## ผลตอบรับ (Feedback)

| หากคุณตอบว่า... | การวิเคราะห์ |
|:---|:---|
|"ส่งทุกครั้งเพื่อความชัวร์" | ❌ ** พัง!** ผู้ใช้จะรำคาญมาก เพราะได้รับแจ้งเตือนซ้ำซ้อนทั้งในแอปและนอกแอป (Double Notification 📱) |
|"ส่งเฉพาะตอนเพื่อนออฟไลน์" | ✅ ** ถูกต้อง!** หากผู้ใช้เชื่อมต่อ WebSocket 📡 อยู่ ข้อมูลควรไหลผ่านทางนั้นเป็นหลัก |
|"ส่งตามสภาวะ Presence + Rate Limiting" | ✅ **Senior-level!** คุณคำนึงถึงทั้งสถานะปัจจุบันของผู้ใช้ และการจำกัดปริมาณเพื่อไม่ให้รบกวนเกินจำเป็น |

**จุดตายที่ Senior ต้องรู้:**Push 📱 Notification 📱 คือทรัพยากรที่มีราคา 💰 (ทั้งค่าส่งและค่าความรำคาญของผู้ใช้) เราต้องมี **Decision Engine ** มาช่วยตัดสินใจก่อนส่งเสมอ

---

## คำอธิบาย (Explain)

### 1. Push Decision Matrix (ตารางตัดสินใจ)

กลยุทธ์ที่ดีที่สุดคือการใช้ Push Notification 📱 เป็นเพียง"สัญญาณปลุก (Wake-up trigger)" โดยไม่ส่งเนื้อหาจริงผ่านทาง Apple/Google เพื่อรักษาความเป็นส่วนตัวและรองรับ End-to-End Encryption [source: WhatsApp Engineering — Security and Privacy Architecture]

| สถานะผู้ใช้ | ประเภทข้อความ | การตัดสินใจ | เหตุผล |
|:---|:---|:---:|---|
|**Online & Active **| ทุกประเภท |** ไม่ส่ง **| ผู้ใช้เห็นข้อความในแอปอยู่แล้ว |
|**Background (< 5 นาที)**| ทั่วไป |**Silent Push 📱**| ปลุกแอปให้มา Fetch ข้อมูลเงียบๆ โดยไม่แสดงแถบแจ้งเตือน |
|**Offline / Background นาน **| ทั่วไป |** ส่งแบบปกติ **| แจ้งเตือนเพื่อให้ผู้ใช้กลับเข้าสู่แอป |
|** ทุกสถานะ **| เร่งด่วน (เช่น Alert) |** ส่งทันที **| ความสำคัญของข้อมูลอยู่เหนือความรำคาญ |

### 2. สถาปัตยกรรมระบบ Push ระดับสูง

เราไม่ได้ส่งตรงจาก Chat Server ไปยัง FCM แต่เราผ่านชั้นกลางที่เรียกว่า **Notification 📱 Service **:
-**Presence Check:** เช็คจาก Redis ว่าผู้ใช้ยังเชื่อมต่อ WebSocket 📡 อยู่หรือไม่?
-**Preference Check:** ผู้ใช้ปิดแจ้งเตือน (Mute) ไว้หรือเปล่า? หรืออยู่ในช่วงเวลา Do Not Disturb (DND)?
-**Device Token Mgmt:** ตรวจสอบว่าผู้ใช้มีกี่อุปกรณ์ (มือถือ, แท็บเล็ต) และส่งไปยังทุก Token ที่ยังใช้งานอยู่ (Valid)

---

## ขยายความ (Extend)

### การจัดการ Device Token (Stale Token Problem)
เมื่อผู้ใช้ลบแอปหรือเปลี่ยนเครื่อง Token เก่าจะยังค้างอยู่ในฐานข้อมูลของเรา:
-  **วิธีแก้ระดับ Senior:** เมื่อส่งผ่าน FCM/APNs แล้วได้รับ Error ว่า"NotRegistered" หรือ"InvalidToken" ระบบต้องทำการลบ Token นั้นทิ้งจากฐานข้อมูลทันที เพื่อลดภาระการส่งในครั้งต่อไป

### Rate Limiting & Cooldown
เพื่อนพิมพ์"สวัสดี""ทำไร""หิวไหม" ภายใน 5 วินาที:
-  **Bad UX:** มือถือสั่น 3 ครั้งติดกัน
-  **Senior Approach:** ใช้ **Cooldown Timer **(เช่น 30 วินาที) ใน Redis หากเพิ่งส่ง Push 📱 ไปยังผู้ใช้คนนี้ในห้องแชทเดิม ให้หยุดส่งชั่วคราวและรวบรวม (Aggregate) ข้อความที่เหลือไว้รอส่งทีเดียวหากผู้ใช้ยังไม่เปิดอ่าน

### กรณีศึกษา: เส้นทางการส่ง Push ในระบบจริง
ในระบบตัวอย่าง:
-   เราใช้ **Google Pub/Sub ** เพื่อแยกโหลดของการส่ง Push 📱 ออกจากระบบหลัก
-  **Decision Engine:** จะทำงานบน Consumer ที่คอยเช็คสถานะจาก MongoDB และ Redis ก่อนจะเรียก FCM API
-  **Trade-off 🤝:** การแยก Service ทำให้มี Latency เพิ่มขึ้นเล็กน้อย (หลักมิลลิวินาที) แต่ช่วยให้ระบบหลักไม่ช้าลงหาก FCM ทำงานช้าหรือล่ม

## จุดตรวจสอบ (Checkpoint)

> **Quick Check:**
> 1."Silent Push 📱" ต่างจาก Push 📱 ปกติอย่างไร?
> 2. ทำไมเราต้องเก็บ Device Token แยกตามอุปกรณ์ของผู้ใช้ 1 คน?
> 3. หากผู้ใช้เปิดแอปค้างไว้แต่ไม่ได้มองจอ (Idle) ระบบควรทำอย่างไร?

<details>
<summary>🎯 ดูเฉลย (คลิกเพื่อเปิด)</summary>

1.**Silent Push 📱** จะไม่มีการสั่นหรือแสดงแถบแจ้งเตือนบนหน้าจอ แต่จะสั่งให้แอปใน Background"ตื่น" ขึ้นมาทำงานบางอย่าง (เช่น Sync ข้อมูล)
2. เพราะผู้ใช้อาจมีหลายอุปกรณ์ (iPhone, iPad) และแต่ละอุปกรณ์มี Token ไม่เหมือนกัน เราต้องส่งให้ครบทุกเครื่องเพื่อให้ผู้ใช้ไม่พลาดข่าวสาร
3. นี่เป็นเคสที่ยาก (Edge Case) — ระบบส่วนใหญ่จะใช้ **Heartbeat ** เพื่อตรวจสอบว่าผู้ใช้ยัง"Active" อยู่จริงไหม หากเงียบไปนานเกินขีดกำหนด (เช่น 5 นาที) จะถือว่า Idle และกลับมาส่ง Push 📱 ตามปกติ

</details>

## สะท้อนคิด (Reflect)

> 💭 ลองนึกถึงแอปที่คุณเพิ่ง"ปิดแจ้งเตือน" หรือ"ลบทิ้ง" ไปล่าสุด เพราะเหตุผลอะไร? เป็นเพราะมันแจ้งเตือนเรื่องไม่สำคัญ หรือแจ้งเตือนบ่อยเกินไปหรือไม่? ในฐานะผู้ออกแบบระบบ คุณจะทำอย่างไรให้ Push 📱 ของคุณเป็นสิ่งที่ผู้ใช้"อยากเห็น" ไม่ใช่"อยากลบ"?
