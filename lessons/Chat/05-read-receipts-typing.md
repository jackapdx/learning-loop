# Read Receipts & Typing Indicators (สถานะข้อความและการพิมพ์)

---

## ปฐมนิเทศ (Orient)

"อ่านแล้ว สีฟ้า" — ฟีเจอร์ที่ดูเหมือนจะเรียบง่ายนี้ แท้จริงแล้วคือฝันร้ายของวิศวกรผู้ออกแบบระบบกระจายตัว (Distributed Systems) เพราะมันสร้างปัญหา **Write Amplification ** มหาศาล: ลองนึกภาพว่า 1 การอ่านของผู้รับ อาจส่งผลให้ต้องอัปเดตสถานะไปยังทุกอุปกรณ์ของผู้ส่งและผู้รับ บทเรียนนี้จะสอนวิธีจัดการ State Machine และเทคนิคการเพิ่มประสิทธิภาพ (Optimization) เพื่อไม่ให้ระบบล่มเพียงเพราะฟีเจอร์"อ่านแล้ว"

---

## ลองทำก่อน (Attempt)

> ** สถานการณ์:** ผู้ใช้ A ส่งข้อความหา B โดยที่ A มี 3 อุปกรณ์ (มือถือ, iPad, คอมพิวเตอร์) และ B ก็มี 2 อุปกรณ์
>
> ** คำถาม:** เมื่อ B เปิดอ่านข้อความบนมือถือ ระบบต้องทำการอัปเดต (Write Operations) ไปยังอุปกรณ์ทั้งหมดกี่จุด? และหาก B ทำการ"เลื่อนอ่าน (Scroll)" 100 ข้อความพร้อมกันในครั้งเดียว ระบบของคุณควรจะส่งเหตุการณ์ (Events) แจ้งเตือน 100 ครั้งเลยหรือไม่?
>
> **✋ หยุดตรงนี้ก่อน **— ลองคิดและคำนวณในใจสักนิด (คำใบ้: อย่าคิดแบบทีละข้อความ!)

## ผลตอบรับ (Feedback)

| หากคุณตอบว่า... | การวิเคราะห์ |
|:---|:---|
|"อัปเดตทุกข้อความที่เลื่อนผ่าน" | ❌ ** หายนะ!** หากเลื่อนผ่าน 100 ข้อความ และมี 3 อุปกรณ์ = 300 Network 📡 Calls ทันที ซึ่งจะทำให้ระบบหน่วงอย่างมาก |
|"ใช้ Batch Update ส่งทีเดียว" | ✅ ** ถูกต้อง!** เราควรส่งเฉพาะหมายเลข ID ของข้อความ"ล่าสุด" ที่อ่านแล้วเพียงครั้งเดียว |
|"Batch + Debounce + Privacy Logic" | ✅ **Senior-level!** คุณคิดครบทั้งเรื่องประสิทธิภาพ (Performance) และความเป็นส่วนตัว (Privacy) ของผู้ใช้ |

**ความลับของมือโปร:** พวกเขาไม่ได้มองว่า"อ่านข้อความที่ 1, 2, 3..." แต่มองว่า **"อ่านถึงข้อความที่ X แล้ว"**(Read up to ID X)

---

### คำอธิบาย (Explain)

ฟีเจอร์"อ่านแล้ว" (Read Receipts) เป็นฟีเจอร์ที่สร้างภาระการเขียน (Write-heavy) มหาศาลให้กับฐานข้อมูล เนื่องจากทุกการเปิดอ่านคือการอัปเดตสถานะ ซึ่งอาจนำไปสู่ปัญหา **Write Amplification ** ในระบบขนาดใหญ่ [source: LinkedIn Engineering — The"Seen" Status Service]

### 1. Message Lifecycle (วงจรชีวิตของข้อความ)


ในการออกแบบระบบแชทระดับ Senior เราต้องจัดการสถานะให้ครบถ้วน:
-  **Sending (🕐):** ข้อความกำลังเดินทางจาก Client ไปหา Server
-  **Sent (✓):**Server ได้รับและบันทึกลงฐานข้อมูลสำเร็จ
-  **Delivered (✓✓):** ข้อความถูกส่งถึงอุปกรณ์ของผู้รับแล้ว (แต่อาจจะยังไม่ได้เปิดดู)
-  **Read (✓✓ สีฟ้า):** ผู้รับเปิดหน้าจอแชทและเห็นข้อความนั้นแล้ว

### 2. วิธีแก้ปัญหา Write Amplification

ปัญหาคือ 1 ข้อความถูกอ่าน = หลายการอัปเดต วิธีแก้คือการใช้ **"Last Read Message ID"**:
-   แทนที่จะบันทึกว่า"ข้อความที่ 1 อ่านแล้ว","ข้อความที่ 2 อ่านแล้ว" ...
-   เราบันทึกแค่เพียง:**"ผู้ใช้ B อ่านถึงข้อความที่ 100 ในห้องแชทนี้แล้ว"**
-   ฝั่งผู้ส่ง (A) เมื่อได้รับสัญญาณนี้ แอปจะทำการเปลี่ยนสถานะข้อความทั้งหมดที่มี ID น้อยกว่าหรือเท่ากับ 100 เป็น"สีฟ้า" ทันทีในครั้งเดียว

### 3. Typing Indicators: สถานะที่เปลี่ยนบ่อยที่สุด
สถานะ"กำลังพิมพ์..." เป็นข้อมูลที่มีอายุสั้นมาก:
-  **ห้ามเก็บลงฐานข้อมูลเด็ดขาด!** เพราะจะสร้างภาระมหาศาล
-  **ใช้ WebSocket 📡 หรือ Redis Pub/Sub:** ส่งสัญญาณสดๆ ไปยังผู้รับและให้แอปฝั่งนั้นแสดงผล
-  **Auto-expire:** หากไม่มีสัญญาณ"พิมพ์" ใหม่เข้ามาภายใน 5-10 วินาที ให้แอปซ่อนสถานะนี้เองอัตโนมัติ เพื่อป้องกันกรณีเน็ตหลุดขณะพิมพ์

## ขยายความ (Extend)

### เทคนิค Optimization: Debounce & Batching
เมื่อผู้ใช้กำลังพิมพ์หรือเลื่อนอ่านอย่างรวดเร็ว:
-  **Debounce:** รอให้ผู้ใช้หยุดกระทำสัก 1-2 วินาทีก่อนจะส่งสัญญาณไปยัง Server
-  **Batching:** รวบรวมคำสั่ง"อ่านแล้ว" ของหลายห้องแชท (ถ้ามี) ส่งไปใน Request เดียว

### เรื่องของความเป็นส่วนตัว (Privacy Trade-off)
แอปแชทที่ดีต้องมีปุ่ม **"ปิดสถานะการอ่าน"**:
-  **Logic:** หากผู้ใช้เลือกปิด เราจะหยุดส่งเหตุการณ์"Read Receipt" ออกจากเครื่องเขา
-  **Trade-off 🤝:** ในเชิงสังคม (Social Contract) หากคุณไม่ให้คนอื่นรู้ว่าคุณอ่านหรือยัง คุณเองก็จะไม่เห็นสถานะการอ่านของคนอื่นเช่นกัน (เหมือนใน WhatsApp/LINE)

### กรณีศึกษา: สถานะเจ้าหน้าที่ในสถาปัตยกรรมระบบแชทจริง
ในระบบตัวอย่างเราบริหารสถานะของเจ้าหน้าที่ (Agent):
-   เราไม่ใช้ Real-time ⏰ Read Receipts แบบวินาทีต่อวินาทีสำหรับลูกค้า
-   แต่เราใช้เพื่อ **Internal Analytics:** เพื่อให้ Supervisor รู้ว่าเจ้าหน้าที่คนไหนเปิดดูเคสแล้วแต่ยังไม่ตอบเกิน 10 นาทีหรือยัง?
-  **วิธีทำ:** เราใช้การอัปเดตสถานะ`last_viewed_at` ใน MongoDB ทุกครั้งที่ Agent เปลี่ยนหน้าตั๋ว (Ticket)

## จุดตรวจสอบ (Checkpoint)

> **Quick Check:**
> 1. ทำไมเราไม่ควรเก็บสถานะ"Typing" ลงใน Database 📦?
> 2."Write Amplification" ในระบบแชทเกิดจากอะไร?
> 3. หากผู้ใช้ A ปิดแอปอยู่ และ B อ่านข้อความของ A ระบบจะแจ้ง A ได้อย่างไร?

<details>
<summary>🎯 ดูเฉลย (คลิกเพื่อเปิด)</summary>

1. เพราะมันเปลี่ยนบ่อยมาก (ทุกการกดแป้นพิมพ์) และไม่มีความสำคัญที่ต้องเก็บไว้เป็นประวัติศาสตร์ การเขียนลง Disk ทุกวินาทีจะทำให้ DB พังโดยไม่จำเป็น
2. เกิดจากการที่การกระทำเพียง 1 อย่างของผู้ใช้ (เช่น การอ่าน) ส่งผลให้ระบบต้องทำการ"เขียน" ข้อมูลลงในหลายๆ จุด (DB, Cache, หลายๆ อุปกรณ์)
3. ใช้ **Silent Push 📱 Notification 📱** เพื่ออัปเดตสถานะใน Background ของแอป A หรือรออัปเดตทันทีที่ A เปิดแอปครั้งต่อไป

</details>
