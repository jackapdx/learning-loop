# Presence Detection (การออกแบบระบบสถานะ Online/Offline)

---

## 🎯 ปฐมนิเทศ (Orient)

ฟีเจอร์"จุดสีเขียว" ที่บอกว่าใครออนไลน์อยู่บ้าง ดูเหมือนจะเป็นเรื่องง่ายๆ แค่เก็บสถานะ`is_online` ไว้ในฐานข้อมูล แต่เมื่อระบบต้องรองรับผู้ใช้หลักล้านคนและสถานะเปลี่ยนไปมาทุกวินาที การใช้ฐานข้อมูลแบบเดิมจะกลายเป็นคอขวดทันที บทเรียนนี้จะสอนวิธีใช้ **Redis ** และ **Heartbeat Mechanisms ** เพื่อสร้างระบบ Presence ที่รวดเร็วและแม่นยำระดับ Senior โดยคำนึงถึงเงื่อนไขที่"แอปไม่ได้บอกลา" เมื่อปิดตัวลง

---

## 🧪 ลองทำก่อน (Attempt)

> ** สถานการณ์:** คุณกำลังออกแบบฟีเจอร์"Online Status" และ"Last Seen" ให้กับแอปแชทที่มีผู้ใช้ 10 ล้านคน โดยมีเงื่อนไขว่าเมื่อผู้ใช้เปิดแอปต้องขึ้น Online ทันที และเมื่อหายไปต้องแสดงเวลาล่าสุดที่ออนไลน์
>
> ** ข้อจำกัด:**
> - ต้องรองรับการอัปเดตสถานะที่เกิดขึ้นบ่อยครั้ง (เช่น ทุกๆ 30 วินาทีต่อคน)
> - ระบบต้องแม่นยำแม้ในกรณีที่ผู้ใช้เน็ตหลุด (Unexpected Disconnection) โดยที่แอปไม่มีโอกาสส่งสัญญาณ"Offline" มาบอก Server
> - ต้องประหยัดภาระการเขียน (Write Load) ของฐานข้อมูลหลักให้มากที่สุด
>
> ** คำถาม:** หากคุณใช้ SQL Database 📦 (เช่น PostgreSQL) ทำการ`UPDATE status = 'online'` ทุกครั้งที่ผู้ใช้ขยับตัว จะเกิดอะไรขึ้นเมื่อมีผู้ใช้พร้อมกัน 1 ล้านคน? และคุณจะออกแบบกลไกอย่างไรให้สถานะกลายเป็น Offline ได้เองโดยอัตโนมัติ?
>
> **✋ หยุดตรงนี้ก่อน **— ลองนึกถึงความแตกต่างระหว่างการ"จดลงกระดาษ (Disk)" กับการ"จำไว้ในหัว (RAM)"

## 💬 ผลตอบรับ (Feedback)

| หากคุณตอบว่า... | การวิเคราะห์ |
|:---|:---|
|"ใช้ SQL แล้วเพิ่ม Index" | ❌ ** พังแน่นอน!**1 ล้าน Updates ต่อวินาทีจะทำให้ Database 📦 เกิด Lock Contention มหาศาล และ Disk I/O จะพุ่งทะลุเพดานจนระบบล่มทั้งระบบ |
|"ใช้ Redis เก็บสถานะ" | ⚠️ ** ใกล้เคียง!**Redis เร็วพอที่จะรับโหลดได้ แต่คุณยังไม่ได้แก้ปัญหาเรื่อง"การลืมบอกลา" หากคุณรอให้ Client ส่ง"Offline" มาอย่างเดียว สถานะจะค้างเป็น Online ตลอดกาลเมื่อเน็ตหลุด |
|"ใช้ Redis + Heartbeat (TTL)" | ✅ **Senior-level!** คุณเข้าใจว่าเราเชื่อใจ Client ไม่ได้ 100% การใช้สัญญาณชีพ (Heartbeat) ร่วมกับคีย์ที่หมดอายุเองได้ (TTL) คือวิธีที่มาตรฐานที่สุดในระบบ Scale ใหญ่ |

**ทำไมการให้เหตุผลแบบนี้สำคัญ?** เพราะวิศวกรอาวุโสต้องออกแบบระบบให้"ทนทานต่อความล้มเหลว" (Fault Tolerant) การที่แอปปิดตัวโดยไม่บอกกล่าวคือสภาวะปกติ (Expected Failure) ที่เราต้องรับมือให้ได้

## 📖 คำอธิบาย (Explain)

### กลยุทธ์สัญญาณชีพ (Heartbeat Mechanism)

ในระดับ Senior เราจะไม่เก็บสถานะ Online/Offline เป็นค่าคงที่ แต่จะใช้แนวคิดของ **"ความสดใหม่ (Freshness)"** ของข้อมูล:

1.**Heartbeat:** เมื่อผู้ใช้ออนไลน์ แอปจะส่งสัญญาณเล็กๆ (Heartbeat) ไปยัง Server ทุกๆ 30 วินาที
2.**Redis SET with TTL:** เมื่อได้รับสัญญาณ Server จะบันทึกลง Redis:
  `SET user:presence:123"online" EX 60` (ตั้งเวลาหมดอายุไว้ 60 วินาที)
3.**Automatic Offline:** หากผู้ใช้เน็ตหลุด สัญญาณชีพจะหายไป และคีย์ใน Redis จะ **Expire ** เองโดยอัตโนมัติ — นี่คือการเปลี่ยนสถานะเป็น Offline ที่แม่นยำและเบาที่สุด

### การแสดงสถานะ"Last Seen"

เราต้องการรู้ว่าเขาหายไปนานแค่ไหนแล้วโดยไม่เพิ่มภาระให้ DB:
-**Online:** ตรวจสอบว่าคีย์`user:presence:123` ยังมีอยู่ใน Redis หรือไม่
-**Last Seen:** บันทึก`last_active_at` ลงใน DB หลัก เฉพาะตอนที่ผู้ใช้เริ่มหายไป (Detect ผ่าน Redis Expire Event) หรือใช้วิธี Batch Update ทุกๆ 5-10 นาทีเพื่อลด Write Load [source: Slack Engineering - Scaling Presence]

## 🔬 ขยายความ (Extend)

### การกระจายสถานะ (Presence Broadcasting)

เมื่อนาย A ออนไลน์ เพื่อนๆ จะรู้ได้อย่างไร?
-**Approach 1: Pull (ช้า):** แอปเพื่อนๆ คอยเรียก API มาเช็ค (เปลืองทรัพยากรและ Latency สูง)
-**Approach 2: Push 📱 via Redis Pub/Sub (เร็ว):** เมื่อนาย A ส่ง Heartbeat, Server จะ"ตะโกน" บอกผ่าน Redis Pub/Sub ไปยัง WebSocket 📡 Server ทุกตัวที่มีเพื่อนของนาย A เชื่อมต่ออยู่

### ปัญหาของ"คนดัง" (The Celebrity Problem)

หากคนที่มี Follower 10 ล้านคนออนไลน์ การ Push 📱 หาทุกคนพร้อมกันจะเกิด **Fan-out Explosion **:
-** วิธีแก้ระดับ Senior:** เราจะไม่ Push 📱 สถานะของคนดังหาทุกคน แต่จะใช้ **Lazy Loading **— คือให้แอปเช็คสถานะเฉพาะเมื่อเปิดหน้าโปรไฟล์หรือหน้าแชทกับคนนั้นจริงๆ เท่านั้น

### กรณีศึกษา: สถาปัตยกรรมสถานะในระบบแชทจริง

ในระบบของเราที่รองรับ Agent หลายช่องทาง:
- ใช้ **Firebase Realtime DB ** เป็นสถานะหลัก เพราะมีฟีเจอร์`onDisconnect` ที่ช่วยเปลี่ยนสถานะใน DB ได้ทันทีที่การเชื่อมต่อ WebSocket 📡 หลุด
-**Trade-off:** เสียค่าใช้จ่ายสูงกว่า Redis แต่ลดความซับซ้อนในการเขียน Backend Logic เองไปได้มหาศาล

## ✅ จุดตรวจสอบ (Checkpoint)

> **Quick Check:**
> 1. ทำไมเราถึงควรตั้ง TTL ใน Redis ให้ยาวกว่าความถี่ของ Heartbeat (เช่น ส่งทุก 30 วิ แต่ TTL 60 วิ)?
> 2."Fan-out" ในระบบ Presence คืออะไร และทำไมมันถึงเป็นอันตรายเมื่อมีผู้ใช้ระดับล้านคน?

<details>
<summary>🎯 ดูเฉลย (คลิกเพื่อเปิด)</summary>

1.** เพื่อเผื่อเวลา (Buffer)**— กรณีเครือข่ายกระตุกเล็กน้อยหรือแอปทำงานช้าลงชั่วคราว สถานะจะได้ไม่กะพริบ (Flapping) เข้าๆ ออกๆ ระหว่าง Online/Offline
2.** การกระจายข้อมูลจาก 1 ไปยัง N ** — เมื่อคน 1 คนเปลี่ยนสถานะ เราต้องส่งข้อมูลหาเพื่อน N คน หาก N มีขนาดใหญ่มาก (เช่น คนดัง) โหลดในการส่งจะสูงจน Server รับไม่ไหว

</details>
