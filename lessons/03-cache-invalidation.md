# Cache Invalidation (ยุทธศาสตร์การจัดการข้อมูลในแคช)

---

## ปฐมนิเทศ (Orient)

มีคำกล่าวอมตะในวงการคอมพิวเตอร์ว่า: *"มีเพียง 2 เรื่องที่ยากที่สุด คือการตั้งชื่อตัวแปร และการทำให้ข้อมูลในแคชเป็นปัจจุบัน (Cache Invalidation)"* การ"ใส่ Redis" ไม่ใช่คำตอบสุดท้าย สิ่งที่แยกวิศวกรระดับอาวุโสออกจากมือสมัครเล่นคือการรู้วิธีรับมือเมื่อข้อมูลต้นทางเปลี่ยนแปลงและการจัดการโหลดมหาศาลเมื่อแคชพัง บทเรียนนี้จะสอนวิธีป้องกันระบบล่มจากปัญหาแคชที่มักถูกมองข้าม

---

## ลองทำก่อน (Attempt)

> **สถานการณ์:** คุณมี API ที่ถูกเรียก 10,000 ครั้งต่อวินาทีเพื่อดึงโปรไฟล์ผู้ใช้ คุณจึงใช้ **Redis Cache ** โดยตั้ง **TTL (Time-To-Live)** ไว้ 5 นาที ทุกอย่างดูเหมือนจะทำงานได้ดี... จนกระทั่งถึงช่วง **Black Friday ** ที่ Traffic พุ่งกระฉูดเป็น 100,000 ครั้งต่อวินาที และแคชยอดนิยมของผู้ใช้จำนวนมากดันหมดอายุ"พร้อมกัน" พอดีในวินาทีนั้น
>
> ** ข้อจำกัด:**
> - Database 📦 ของคุณรองรับได้สูงสุดเพียง 5,000 TPS (Transactions Per Second)
> - ไม่สามารถเพิ่มงบประมาณเพื่อขยาย Database 📦 (Vertical Scaling) ได้ทันที
>
> ** คำถาม:** จะเกิดอะไรขึ้นกับ Database 📦 ของคุณ? และในฐานะ Senior Engineer คุณจะปรับกลยุทธ์การตั้ง TTL หรือการดึงข้อมูลอย่างไรเพื่อป้องกันหายนะนี้?
>
> **✋ หยุดตรงนี้ก่อน **— ลองนึกภาพเหตุการณ์"เขื่อนแตก" เมื่อ Request แสนตัวรุมถล่มฐานข้อมูลที่รับได้เพียงห้าพัน

## ผลตอบรับ (Feedback)

| หากคุณตอบว่า... | การวิเคราะห์ |
|:---|:---|
|"ตั้ง TTL ให้นานขึ้น" | ⚠️ ** แค่เลื่อนปัญหาออกไป!** ข้อมูลจะเก่าเกินไป (Stale) และปัญหาเดิมจะกลับมาอีกครั้งเมื่อ TTL นั้นหมดอายุลงในช่วง Peak Traffic |
|"ทำ Cache Warm-up ก่อนหมดอายุ" | ⚠️ ** ดีแต่ซับซ้อน!** คุณต้องใช้ทรัพยากรเพิ่มเพื่อทำนายว่าคีย์ไหนจะหมดอายุเมื่อไหร่ ซึ่งอาจไม่คุ้มค่าในระบบที่มีข้อมูลหลากหลาย |
|"ใช้ Jitter (สุ่มเวลาหมดอายุ) + Mutex Lock" | ✅ ** คิดแบบ Senior!** การสุ่มเวลา (Jitter) ช่วยกระจายโหลด และ Mutex Lock รับประกันว่าจะมีเพียง Request เดียวที่ไปดึงข้อมูลจาก DB เพื่อลดภาระเขื่อนแตก |

**ทำไมการให้เหตุผลแบบนี้สำคัญ?** เพราะวิศวกรอาวุโสมองว่า"การหมดอายุของแคช" คือความเสี่ยง (Risk) ไม่ใช่แค่การลบข้อมูลทิ้ง การออกแบบระบบที่ทนทานต่อสภาวะ Peak คือหัวใจสำคัญ

## คำอธิบาย (Explain)

### 3 ปรากฏการณ์"หายนะ" ของระบบแคช

| ปรากฏการณ์ | อาการ | สาเหตุ/ผลกระทบ |
|:---:|---|---|
|**Cache Stampede **| แคชยอดนิยมหมดอายุพร้อมกัน | Request มหาศาลทะลักเข้า DB โดยตรง ทำให้ DB น็อคและระบบล่มทั้งระบบ (Cascading Failure) |
|**Cache Penetration **| ค้นหาข้อมูลที่"ไม่มีอยู่จริง" ซ้ำๆ | Request ทะลุแคช (เพราะข้อมูลไม่มีในแคช) ไปถึง DB ทุกครั้ง มักเกิดจากการโดนยิงถล่มด้วย ID ที่สุ่มขึ้นมา |
|**Cache Avalanche **| แคชจำนวนมากพังหรือหมดอายุพร้อมกัน | อาจเกิดจาก Redis Server ล่ม หรือการตั้ง TTL เท่ากันหมด ทำให้ DB รับโหลดไม่ไหว |

### กลยุทธ์การอัปเดตข้อมูล (Update Strategies)

1.**Cache-aside (Lazy Loading):** แอปอ่านจากแคชก่อน ถ้าไม่มี (Cache Miss) ค่อยไปอ่าน DB แล้วเขียนกลับลงแคช
    *   *สิ่งที่ต้องแลก:* ข้อมูลอาจจะเก่า (Stale) หากไม่มีการลบแคชเมื่อ DB อัปเดต
2. **Write-through:** เขียนข้อมูลลงแคชและ DB พร้อมกันใน Transaction เดียว
    *   *สิ่งที่ต้องแลก:* การเขียนช้าลง (Latency เพิ่ม) แต่รับประกันความถูกต้อง (Strong Consistency ⛓️)
3. **Write-behind (Write-back):** เขียนลงแคชทันที แล้วค่อย Sync ลง DB แบบ Asynchronous
    *   *สิ่งที่ต้องแลก:* เสี่ยงข้อมูลหายถ้าแคชล่มก่อนจะ Sync ลง DB (เหมาะสำหรับ Log หรือ Metric)

## ขยายความ (Extend)

### เทคนิคขั้นสูงสำหรับ Senior

**1. Jitter (Probabilistic Expiration):**
แทนที่จะตั้ง`TTL = 300` วินาทีเป๊ะๆ ให้ใช้การสุ่มช่วงเวลาเพื่อให้แคชทยอยหมดอายุ:
```python
# ดีกว่า: กระจายโหลดการ Rebuild แคช
base_ttl = 300
jitter = random.randint(-30, 30) 
set_cache(key, value, base_ttl + jitter)
```

**2. Mutex Lock (SET NX):**
ใช้เทคนิค"Single Flight" โดยให้ Request แรกที่เจอ Cache Miss เป็นคนจอง Lock เพื่อไปดึง DB ส่วน Request อื่นๆ ที่ตามมาให้รอหรือใช้ข้อมูลเก่าไปก่อน:
```redis
# ใช้ SET with NX (Not Exists) เพื่อจองสิทธิ์ดึงข้อมูล
SET lock:profile:123"locked" NX EX 5
```

**3. Bloom Filter:**
เพื่อแก้ปัญหา **Cache Penetration **(ข้อมูลที่ไม่มีจริง) ให้ใช้ Bloom Filter ตรวจสอบก่อนว่า ID นั้น"น่าจะมี" ใน DB หรือไม่ก่อนจะส่ง Request ไปถล่ม DB [source: Redis Documentation - Bloom Filters]

## จุดตรวจสอบ (Checkpoint)

> **Quick Check:**
> 1. ทำไมการใช้`FlushAll` ใน Redis บน Production ถึงเป็นเรื่องต้องห้ามในช่วงที่มี Traffic สูง?
> 2. หากระบบต้องการความถูกต้องของข้อมูลระดับ 100% (เช่น ยอดเงิน) คุณควรใช้กลยุทธ์อัปเดตแคชแบบใด?

<details>
<summary>🎯 ดูเฉลย (คลิกเพื่อเปิด)</summary>

1.** เพราะจะทำให้เกิด Cache Avalanche **— ข้อมูลทั้งหมดหายไปทันที ทำให้ทุก Request วิ่งตรงไปหา Database 📦 พร้อมกันจน DB ล่ม
2.**Write-through หรือ Cache-aside พร้อมลบแคชทันทีเมื่ออัปเดต DB ** — เพื่อรับประกันว่า Client จะไม่เห็นข้อมูลเก่าในแคช แต่ต้องแลกด้วย Latency ที่สูงขึ้นในการเขียน

</details>
