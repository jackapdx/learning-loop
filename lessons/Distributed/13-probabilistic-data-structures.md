# Probabilistic Data Structures (โครงสร้างข้อมูลเชิงสถิติ: Bloom Filters & HyperLogLog)

---

## ปฐมนิเทศ (Orient)

เมื่อระบบของคุณขยายตัวไปถึงระดับร้อยล้านหรือพันล้านผู้ใช้ (Google, Meta, Netflix Scale) การเก็บข้อมูลเพื่อหาคำตอบง่ายๆ เช่น"User คนนี้เคยดูวิดีโอนี้หรือยัง?" หรือ"วันนี้มีคนเข้าเว็บไม่ซ้ำกัน (Unique Visitors) กี่คน?" จะเริ่มกิน RAM มหาศาลจนระบบแบกไม่ไหว **Probabilistic Data Structures ** คือ"เวทมนตร์" ที่ช่วยให้เราตอบคำถามเหล่านี้ได้โดยใช้หน่วยความจำเพียงไม่กี่ KB โดยแลกกับ ** ความแม่นยำที่ลดลงเพียงเล็กน้อย **

---

## ลองทำก่อน (Attempt)

> ** สถานการณ์:** คุณกำลังออกแบบระบบ"Anti-Spam" สำหรับอีเมลที่มีผู้ใช้ 1,000 ล้านคน
> 
> ** โจทย์:**
> 1. เมื่อมีอีเมลส่งเข้ามา ต้องเช็คว่า URL ในอีเมลอยู่ในรายชื่อ"Phishing Site" หรือไม่ (มีรายชื่อ 1,000 ล้าน URL)
> 2. การเช็คต้องเร็วมาก (ระดับ Microseconds) และไม่ควรไปรัน SQL ทุกครั้ง
> 3. มีข้อจำกัดเรื่อง RAM บน Edge Server (มีให้แค่ 100MB สำหรับงานนี้)
> 
> ** คำถาม:** คุณจะใช้วิธีใดในการจัดเก็บข้อมูล URL พันล้านรายการนี้เพื่อให้เช็คได้เร็วและใช้ RAM น้อยที่สุด? และ"สิ่งที่ต้องแลก (Trade-off)" คืออะไร?
>
> **✋ หยุดตรงนี้ก่อน **— ลองนึกดูว่าการใช้ Hash Set ปกติจะใช้ RAM เท่าไหร่ (สมมติ URL ละ 50 bytes) และทำไมมันถึงเป็นไปไม่ได้ในโจทย์นี้

## ผลตอบรับ (Feedback)

| หากคุณตอบว่า... | การวิเคราะห์ |
|:---|:---|
|"ใช้ Redis Hash Set" | ❌ **RAM พัง!**1,000 ล้าน URL x 50 bytes = อย่างน้อย 50GB! เกินโควต้า 100MB ไปมหาศาล |
|"ใช้ Bloom Filter" | ✅ ** นี่คือคำตอบระดับ Senior!**Bloom Filter สามารถเก็บข้อมูลพันล้านรายการในหลัก MB ได้ โดยไม่มีวันบอกว่า"ไม่มี" ถ้ามีอยู่จริง (Zero False Negatives) แต่"อาจจะ" บอกว่ามีทั้งที่ไม่มีจริง (False Positives) |
|"ใช้ HyperLogLog" | ⚠️ ** ผิดจุดประสงค์!**HyperLogLog ใช้สำหรับนับจำนวนที่ไม่ซ้ำ (Cardinality) แต่ไม่สามารถบอกได้ว่า"สมาชิกตัวไหน" อยู่ใน Set หรือไม่ |

**ทำไมการให้เหตุผลแบบนี้สำคัญ?** เพราะในระบบระดับโลก เรายอมรับ **"ความไม่แน่นอนที่ควบคุมได้"** เพื่อแลกกับ **"ความสามารถในการขยายตัว (Scalability)"** การรู้ว่าเครื่องมือไหนยอมรับ Error แบบไหนคือหัวใจของ System Design [source: Burton H. Bloom — Space/Time Trade-offs in Hash Coding with Allowable Errors]

## คำอธิบาย (Explain)

### 1. Bloom Filter: เช็คว่า"มีอยู่หรือไม่?"

Bloom Filter คือ Bit Array ขนาดใหญ่ที่ทำงานร่วมกับหลาย Hash Functions:
-** การเพิ่มข้อมูล:**Hash ข้อมูลแล้วเปลี่ยน Bit ในตำแหน่งนั้นเป็น 1
-** การเช็คข้อมูล:**Hash ข้อมูลแล้วดูว่า Bit ทุกตำแหน่งเป็น 1 หรือไม่

| คุณสมบัติ | คำอธิบาย |
|---|---|
|**False Positive **| ⚠️ มีโอกาสบอกว่า"มี" ทั้งที่ไม่มี (เพราะ Hash ชนกัน) |
|**False Negative **| ✅ ** ไม่มีทางเกิดขึ้น ** ถ้า Bloom Filter บอกว่า"ไม่มี" คือไม่มีแน่นอน 100% |
|** การลบข้อมูล **| ❌ ลบไม่ได้ (เพราะการลบ Bit หนึ่งอาจกระทบข้อมูลตัวอื่น) |

### 2. HyperLogLog: นับจำนวนที่ไม่ซ้ำ (Unique Count)

ถ้าคุณต้องการนับ Unique Users รายวันของ Facebook (3,000 ล้านคน) การใช้ Set จะกิน RAM หลาย GB แต่ HyperLogLog ใช้เพียง **1.5 KB ** เท่านั้น! โดยมีค่าความคลาดเคลื่อนเฉลี่ยเพียง **0.81%**

### ตารางเปรียบเทียบ

| เครื่องมือ | ปัญหาที่แก้ | พื้นที่ที่ใช้ | ความแม่นยำ |
|---|---|---|---|
|**Set / Hash Table **| เก็บข้อมูลจริง | มหาศาล (Linear) | 100% |
|**Bloom Filter **| เช็คการเป็นสมาชิก | น้อยมาก (Fixed) | อาจจะมีเกิน (False Positive) |
|**HyperLogLog **| นับจำนวนไม่ซ้ำ | น้อยที่สุด (Fixed) | คลาดเคลื่อนเล็กน้อย (~1%) |

## ขยายความ (Extend)

### การนำไปใช้ในระบบกระจายจริง (Production Use Cases)

1.**Cassandra / BigTable:** ใช้ Bloom Filter เช็คในหน่วยความจำก่อนว่า Key นี้อยู่ในไฟล์ข้อมูลบน Disk (SSTable) หรือไม่ ถ้า"ไม่มีแน่ๆ" จะได้ไม่ต้องเสียเวลาเปิดไฟล์ (Reduce Disk I/O)
2.**Google Safe Browsing:**Chrome ใช้ Bloom Filter เก็บรายชื่อเว็บอันตรายไว้ในเครื่องผู้ใช้ เพื่อเช็คเบื้องต้นได้ทันทีโดยไม่ต้องถาม Server ทุกครั้ง
3.**Medium:** ใช้ Bloom Filter เช็คว่า User เคยอ่านบทความนี้หรือยัง เพื่อไม่ให้แนะนำซ้ำ

### ข้อควรระวังระดับ Senior
1.**The Size Problem:**Bloom Filter ต้องกำหนดขนาดล่วงหน้า ถ้าข้อมูลเยอะเกินไป Bit จะเต็มและ False Positive Rate จะพุ่งสูงขึ้น (ต้องทำ Dynamic Bloom Filter หรือสร้างอันใหม่)
2.**Hashing Overhead:** การใช้ Hash Function เยอะๆ ช่วยลด Error แต่กิน CPU มากขึ้น ต้องบาลานซ์ให้ดี
3.**JS/API Limits:** เมื่อส่ง HyperLogLog หรือ Bloom Filter (Binary Data) ผ่าน API ต้องจัดการเรื่อง Serialization ให้มีประสิทธิภาพ

## จุดตรวจสอบ (Checkpoint)

> **Quick Check:**
> 1. ถ้า Bloom Filter บอกว่า"ไม่มีข้อมูลนี้" (Not Found) เราสามารถเชื่อถือได้กี่เปอร์เซ็นต์?
> 2. ในระบบระบบหนึ่ง คุณต้องการนับว่า"มี User ที่ไม่ซ้ำกันกี่คนมาดูไลฟ์สด" โดยยอมรับความผิดพลาดได้บ้าง คุณควรเลือกอะไร?
> 3. ทำไมการใช้ Bloom Filter ถึงช่วยลด Disk I/O ได้มหาศาลในฐานข้อมูลประเภท NoSQL?

<details>
<summary>🎯 ดูเฉลย (คลิกเพื่อเปิด)</summary>

1.**100%**— เพราะ Bloom Filter ไม่มีทางเกิด False Negative ถ้าผลบอกว่าไม่มี คือไม่มีแน่นอน
2.**HyperLogLog **— เพราะโจทย์ต้องการ"นับจำนวนไม่ซ้ำ" (Cardinality estimation) ไม่ใช่เช็คสมาชิกรายตัว
3.** เพราะมันเป็น"ด่านหน้า" ใน RAM ** — มันช่วยกรอง Request ที่จะหาข้อมูลที่"ไม่มีอยู่จริง" ออกไปได้ทันที ทำให้ฐานข้อมูลไม่ต้องไปค้นหาไฟล์ใน Disk ที่ทำงานช้ากว่า RAM มหาศาล
