# VACUUM & MVCC (ทำไมฐานข้อมูลถึงบวม และวิธีแก้)

---

## ปฐมนิเทศ (Orient)

คุณเคยสงสัยไหมว่าทำไม PostgreSQL ถึงสามารถให้ผู้ใช้คนหนึ่ง"อ่าน" ข้อมูลในขณะที่ผู้ใช้คนอื่นกำลัง"เขียน" ข้อมูลตัวเดียวกันได้โดยไม่ต้องรอ? คำตอบคือ **MVCC (Multi-Version Concurrency Control)**

แต่เหรียญมีสองด้านเสมอ กลไกนี้ทำให้เกิดสิ่งที่เรียกว่า **"Dead Tuples"**(ข้อมูลที่ถูกลบแต่ยังค้างอยู่ใน Disk) ซึ่งหากจัดการไม่ดี จะนำไปสู่ปัญหา **Database Bloat **(ตารางบวม) ที่ทำให้ประสิทธิภาพตกลงอย่างมหาศาล บทเรียนนี้จะสอนให้คุณเข้าใจกลไกเบื้องหลังและวิธีคุมบังเหียน **Auto-VACUUM ** ให้ทำงานได้อย่างสมบูรณ์

---

## ลองทำก่อน (Attempt)

> ✍️ ** สถานการณ์:** คุณมีตาราง`orders` ที่มีการ UPDATE สถานะวันละ 1 ล้านครั้ง ทุกเช้าคุณสังเกตว่าตารางนี้กินพื้นที่เพิ่มขึ้นเรื่อยๆ ทั้งที่จำนวนแถว (Rows) ยังเท่าเดิม ประสิทธิภาพการสแกนตาราง (Seq Scan) ก็ช้าลงเรื่อยๆ
>
> ** คำถาม:** เกิดอะไรขึ้นในระดับ Disk? และทำไมการรันคำสั่ง`DELETE` ถึงไม่ทำให้พื้นที่ Disk คืนกลับมายัง OS ทันที?

**หยุดคิดสักครู่ **— ลองจินตนาการว่า PostgreSQL จัดการกับการแก้ไขข้อมูลอย่างไร...

### คำอธิบาย (Explain)

PostgreSQL ใช้ระบบ Snapshot เพื่อให้แต่ละ Transaction เห็นข้อมูลในเวอร์ชันที่ถูกต้องของตัวเอง โดยใช้หลักการที่ว่าการ"อ่าน" ไม่ขัดแย้งกับการ"เขียน" (Readers do not block writers, and writers do not block readers) [source: PostgreSQL Documentation — Concurrency Control]

### 1. MVCC: ความลับของการอ่าน/เขียนพร้อมกัน

PostgreSQL ใช้ระบบ Snapshot เพื่อให้แต่ละ Transaction เห็นข้อมูลในเวอร์ชันที่ถูกต้องของตัวเอง
*   เมื่อคุณ`UPDATE`: Postgres จะเขียนแถวใหม่ (New Version) และมาร์คแถวเก่าเป็น"Expired"
*   เมื่อคุณ`DELETE`: Postgres แค่มาร์คแถวว่า"Deleted" (ยังไม่ลบจริง)
*   **ข้อดี:** การ"อ่าน" (SELECT) จะไม่ Block การ"เขียน" (UPDATE/DELETE) เลย!

### 2. Dead Tuples และปัญหาตารางบวม (Bloat)
แถวที่ถูกมาร์ค Expired/Deleted ไปแล้วเรียกว่า **Dead Tuples **
*   หากเรามีตาราง 1 ล้านแถว และอัปเดตทุกแถว 1 ครั้ง เราจะมี 1 ล้าน Live Tuples และ 1 ล้าน Dead Tuples
*   PostgreSQL ต้องสแกนผ่าน Dead Tuples เหล่านี้ด้วย ทำให้ Query ช้าลงมาก

### 3. VACUUM: พนักงานทำความสะอาด
หน้าที่ของ VACUUM คือการเข้าไปกวาดล้าง Dead Tuples เพื่อให้พื้นที่นั้นกลับมาใช้งานใหม่ได้
*   **Standard VACUUM:** ทำความสะอาดพื้นที่ให้ Postgres นำไปใช้ใหม่ได้ (ไม่ต้อง Lock ตาราง)
*   **VACUUM FULL:** บีบอัดตารางใหม่เพื่อให้คืนพื้นที่ให้ OS (** อันตราย:** มันจะ Lock ตารางทั้งใบแบบ Exclusive ห้ามใช้ใน Production)
*   **Auto-VACUUM:** ระบบอัตโนมัติที่รันเบื้องหลัง (แนะนำให้เปิดและตั้งค่าให้เหมาะสมเสมอ)

## ขยายความ (Extend)

### การตั้งค่า Auto-VACUUM ให้ทำงานดุดันขึ้น (Tuning)
ในระบบที่มีการเขียนข้อมูลสูง (High Write Load) ค่า Default ของ Auto-VACUUM มักจะช้าเกินไปจนทำความสะอาดไม่ทัน
```sql
-- ตัวอย่างการปรับแต่งเฉพาะตารางที่มีการอัปเดตบ่อย
ALTER TABLE big_table SET (
  autovacuum_vacuum_scale_factor = 0.01,  -- เริ่มทำงานเมื่อมี Dead Tuples แค่ 1% (แทนที่จะเป็น 20%)
  autovacuum_vacuum_cost_limit = 1000     -- ให้ทรัพยากรเพิ่มขึ้นเพื่อให้ทำงานเสร็จไวขึ้น
);
```

### Transaction ID (XID) Wraparound: หายนะที่เงียบเชียบ
PostgreSQL มีขีดจำกัดของหมายเลข Transaction (ประมาณ 2 พันล้าน) หาก VACUUM ไม่ได้รันนานเกินไปจนเลขรันมาชนกัน ** ฐานข้อมูลจะ Shutdown ตัวเองเพื่อป้องกันข้อมูลเสียหาย **
*   **วิธีป้องกัน:** ตรวจสอบ`age(relfrozenxid)` ของทุกตารางเสมอผ่านระบบ Monitoring

### การตรวจสอบ Bloat
คุณสามารถใช้ Extension อย่าง`pgstattuple` เพื่อดูว่าตอนนี้ตารางของคุณมี Dead Tuples อยู่กี่เปอร์เซ็นต์
```sql
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstattuple('orders');
-- ดูค่า dead_tuple_percent ถ้าเกิน 20% ควรเริ่มกังวล
```

## จุดตรวจสอบ (Checkpoint)

🎯 **Quick Check:**
MVCC ย่อมาจากอะไร และประโยชน์สูงสุดของมันคืออะไร?
ทำไมเราถึงไม่ควรใช้`VACUUM FULL` บนตารางที่มีคนใช้งานอยู่?
หากคุณลบข้อมูล 50% ของตาราง แต่ขนาดไฟล์ใน OS ไม่ลดลง เป็นเรื่องปกติหรือไม่?

<details>
<summary>ดูเฉลย (คลิกเพื่อเปิด)</summary>

**Multi-Version Concurrency 🧵 Control **- ประโยชน์คือทำให้การ"อ่าน" ไม่ Block การ"เขียน"
เพราะมันจะ **Lock ตารางแบบ Exclusive ** ทำให้ไม่มีใครสามารถ Query หรือเขียนข้อมูลได้เลยจนกว่าจะเสร็จ (Downtime)
**ปกติมาก ** - พื้นที่ที่ถูกลบจะกลายเป็นช่องว่าง (Free Space) ภายในไฟล์เดิมเพื่อให้ PostgreSQL เขียนข้อมูลใหม่ทับลงไปได้

</details>
