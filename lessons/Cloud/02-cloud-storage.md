# Cloud Storage: ยุทธศาสตร์การเก็บข้อมูลระดับ Petabyte

---

## 🎯 ปฐมนิเทศ (Orient)

*"ทำไมเราไม่เก็บรูปผู้ใช้ไว้ใน Hard Disk ของเซิร์ฟเวอร์เหมือนเดิม?"* ในยุคคลาวด์ การเก็บไฟล์ไว้ในเครื่อง (Local Storage) คือจุดเริ่มต้นของหายนะ เพราะมันสเกลไม่ได้และเสี่ยงข้อมูลหายหากเครื่องพัง **Cloud Storage (Object Storage)** คือคำตอบที่มาพร้อมกับความทนทาน 99.999999999% บทเรียนนี้จะสอนวิธีจัดการไฟล์มหาศาลให้ประหยัดเงินและปลอดภัยที่สุด

---

## 🧪 ลองทำก่อน (Attempt)

> ✍️**สถานการณ์**:คุณกำลังทำแอป Streaming วิดีโอที่มีไฟล์รวมกันกว่า **1 PB (1,000 TB)**> - วิดีโอใหม่จะถูกดูบ่อยมากใน 30 วันแรก
> - หลังจากนั้น 90% ของวิดีโอแทบไม่มีใครกดดูเลย
> - คุณต้องการให้ User สามารถอัปโหลดไฟล์ตรงเข้า Storage ได้โดยไม่ต้องผ่านเซิร์ฟเวอร์ของคุณ (เพื่อประหยัด Bandwidth)
>
>**คำถาม**:ในฐานะ Senior Engineer คุณจะใช้ฟีเจอร์ใดของ Cloud Storage เพื่อ 1) ลดค่าใช้จ่าย และ 2) ให้ User อัปโหลดไฟล์ได้อย่างปลอดภัย?
>
>**หยุดตรงนี้ก่อน**— ลองนึกถึงคำว่า **Lifecycle** และ **Signed URL**---

## 💬 ผลตอบรับ (Feedback)

| หากคุณตอบว่า... | การวิเคราะห์ |
|:---|:---|
|"เก็บไว้ใน Standard Class ตลอดไป" | ❌**ผลาญงบ!** การเก็บไฟล์ 1PB ที่ไม่มีคนดูใน Standard Class จะทำให้บริษัทล้มละลายได้จากค่าเช่าที่แพงเกินจำเป็น |
|"ใช้ Lifecycle Management" | ✅**ถูกต้อง!** คุณควรย้ายไฟล์ที่ไม่มีคนดูไปอยู่ใน Coldline หรือ Archive Class อัตโนมัติเพื่อลดค่าใช้จ่ายลงกว่า 10 เท่า |
|"ให้ User ส่งไฟล์ผ่าน API ของเรา" | ⚠️**คอขวด!** เซิร์ฟเวอร์คุณจะรับโหลดไม่ไหว (Network 📡 IO) คุณควรใช้ **Signed URLs** เพื่อให้ User คุยกับ Storage ได้โดยตรง |**ทำไมคนส่วนใหญ่ถึงพลาด?** เพราะเรามักมอง Cloud Storage เป็นแค่"ตู้เก็บของ" แต่ลืมมองเรื่อง **Cost Tiering** และ **Security Delegation** ซึ่งเป็นหัวใจของการจัดการข้อมูลขนาดใหญ่

## 📖 คำอธิบาย (Explain)

### 1. Storage Classes: ยิ่งเก็บนาน ยิ่งจ่ายถูก

หัวใจของการประหยัดเงินคือการเลือก"ชั้น" ของการเก็บข้อมูล:
-**Standard**: สำหรับข้อมูลที่เข้าถึงบ่อย (Hot Data)
-**Nearline**: สำหรับข้อมูลที่เข้าถึงไม่เกินเดือนละครั้ง (Backup)
-**Coldline**: สำหรับข้อมูลที่เข้าถึงไม่เกินไตรมาสละครั้ง
-**Archive**: สำหรับข้อมูลที่ต้องเก็บตามกฎหมาย (Compliance) แทบไม่มีคนดู

### 2. Object Lifecycle Management

อย่ารัน Script ลบไฟล์เอง ให้ใช้ระบบอัตโนมัติ:
-**Rule**: "ถ้าไฟล์มีอายุเกิน 30 วัน ให้ย้ายจาก Standard ไป Nearline"
-**Rule**: "ถ้าไฟล์มีอายุเกิน 365 วัน ให้ลบทิ้งทันที"

### 3. Signed URLs (กุญแจชั่วคราว)

แทนที่จะเปิด Bucket เป็น Public (อันตรายมาก!) หรือรับไฟล์ผ่าน API (ช้า ⚡):
User ขอสิทธิ์อัปโหลดจาก Backend
Backend สร้าง **Signed URL**(กุญแจที่มีอายุ 5 นาที) ส่งให้ User
User นำกุญแจนี้ไปอัปโหลดไฟล์เข้า Storage ตรงๆ อย่างปลอดภัย

## 🔬 ขยายความ (Extend)

### ยุทธศาสตร์ Senior: การตั้งชื่อไฟล์เพื่อ Performance

ใน Cloud Storage บางเจ้า (เช่น S3 ยุคเก่า) การตั้งชื่อไฟล์แบบเรียงลำดับ (เช่น`image_001.jpg`,`image_002.jpg`) อาจทำให้เกิด **Hotspot** ในระบบจัดเก็บ:
- *เทคนิค:* ใช้ **Hash Prefix**(เช่น`a1b2_image_001.jpg`) เพื่อกระจายไฟล์ไปอยู่คนละ Partition ของระบบคลาวด์ ช่วยให้ดึงข้อมูลเร็วขึ้นมหาศาล

### ความต่างที่สำคัญ

| ประเภท | Cloud Storage (Object) | Persistent Disk (Block) |
|:---|:---:|:---:|
|**ความจุ**| ไม่จำกัด (Unlimited) | จำกัดตามขนาดที่ซื้อ |
|**การดึงข้อมูล**| ผ่าน HTTP API | ต้อง Mount เข้ากับเครื่อง |
|**ความเร็ว**| Latency สูงกว่า | Latency ต่ำมาก (เหมาะกับ DB) |

## ✅ จุดตรวจสอบ (Checkpoint)

🎯**Quick Check:** หากต้องการเก็บ Log ย้อนหลัง 5 ปีที่แท้จริงไม่เคยเปิดดูเลย Class ไหนถูกที่สุด?
Signed URL ช่วยลดโหลดของเซิร์ฟเวอร์ Backend ได้อย่างไร?
ทำไมเราถึงไม่ควรใช้ Cloud Storage มาติดตั้ง OS หรือรัน Database 📦?

<details>
<summary>ดูเฉลย (คลิกเพื่อเปิด)</summary>**Archive Storage**(ถูกที่สุด แต่เสียค่าดึงข้อมูลแพงและใช้เวลาดึงนาน)
ช่วยให้ User **รับ-ส่งข้อมูลกับ Storage ได้โดยตรง** ไม่ต้องผ่าน Bandwidth และ CPU ของ Backend
เพราะ Cloud Storage คือ **Object Storage** ซึ่งเข้าถึงข้อมูลทีละชิ้นใหญ่ๆ ผ่าน HTTP ไม่ได้ออกแบบมาเพื่อการอ่าน/เขียนระดับ Byte (Random Access) ที่รวดเร็วเหมือน Hard Disk (Block Storage)

</details>
