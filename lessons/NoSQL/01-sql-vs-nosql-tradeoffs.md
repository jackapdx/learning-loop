# SQL vs NoSQL: เมื่อไหร่ที่ความยืดหยุ่นกลายเป็นหายนะ?

---

## ปฐมนิเทศ (Orient)

*"ใช้ MongoDB สิ มันไม่มี Schema สเกลได้ไม่จำกัด!"* — คำกล่าวนี้คือกับดักที่ทำให้นักพัฒนาจำนวนมากต้องเสียน้ำตามาแล้วเมื่อระบบเริ่มโต ในโลกความจริง NoSQL ไม่ได้ถูกเลือกเพียงเพราะ"ความง่าย" แต่ถูกเลือกเพราะ **"ข้อจำกัดทางกายภาพ"** ของ Hardware บทเรียนนี้จะสอนให้คุณเข้าใจว่าเมื่อไหร่ควรใช้ SQL และเมื่อไหร่ที่ต้องตัดใจไป NoSQL ผ่านกรณีศึกษาของ **Discord **

---

## ลองทำก่อน (Attempt)

> ✍️ ** สถานการณ์:** คุณใช้ **MongoDB ** เก็บข้อความแชท (Chat Messages) 
> - เริ่มแรกมีผู้ใช้ 1 แสนคน ทุกอย่างรวดเร็วมาก
> - ผ่านไป 1 ปี ข้อมูลเพิ่มเป็น **100 ล้านข้อความ **
> - จู่ๆ ระบบเริ่ม"อืด" อย่างหาสาเหตุไม่ได้ ทั้งที่ CPU ของเซิร์ฟเวอร์ยังว่าง (แค่ 10-20%)
> - เมื่อตรวจสอบพบว่า Disk I/O พุ่งสูงลิบ (Disk Thrashing)
>
> ** คำถาม:** ในฐานะ Senior Engineer คุณคิดว่าสาเหตุที่แท้จริงคืออะไร? และการ"เพิ่ม RAM" จะแก้ปัญหานี้ได้ถาวรหรือไม่?
>
> ** หยุดตรงนี้ก่อน **— ลองนึกถึงคำว่า **Working Set **(ชุดข้อมูลที่ถูกเรียกบ่อย)

## ผลตอบรับ (Feedback)

| หากคุณตอบว่า... | การวิเคราะห์ |
|:---|:---|
|"Schema มันใหญ่เกินไป" | ❌ ** ไม่ใช่สาเหตุ!** ปัญหาไม่ได้อยู่ที่โครงสร้างข้อมูล แต่อยู่ที่ว่าข้อมูลนั้น"ถูกจัดเก็บ" อย่างไรบนดิสก์ |
|"Index มันใหญ่เกินกว่า RAM" | ✅ ** นี่คือคำตอบ!**(Working Set) เมื่อ Index ทั้งหมดโหลดลง RAM ไม่ไหว MongoDB ต้องสลับข้อมูลเข้าออกดิสก์ตลอดเวลา (Paging) ทำให้ช้าลงมหาศาล |
|"เพิ่ม RAM ไปเรื่อยๆ" | ⚠️ ** แค่ซื้อเวลา!** ข้อมูลระดับพันล้านแถวจะไม่มี RAM ตัวไหนในโลกรับไหว คุณต้องเปลี่ยนสถาปัตยกรรม (Horizontal Scaling) |

**ทำไมคนส่วนใหญ่ถึงพลาด?** เพราะเรามักคิดว่า Database 📦 สเกลได้ด้วยการเพิ่มความแรงเครื่อง (Vertical) แต่ลืมไปว่า NoSQL ถูกสร้างมาเพื่อแก้ปัญหาเมื่อ **"ข้อมูลใหญ่เกินกว่าที่เครื่องเดียวจะเก็บ Index ไหว"**

### คำอธิบาย (Explain)

การเลือกประเภทของฐานข้อมูลคือการเลือกระหว่าง"ความยืดหยุ่นของความสัมพันธ์" (SQL) และ"ความยืดหยุ่นของการขยายตัว" (NoSQL) ตามพฤติกรรมการเข้าถึงข้อมูลของแอปพลิเคชัน [source: AWS Documentation — SQL vs. NoSQL Databases]

### 1. Working Set: ปัจจัยตัดสินชีวิต

Working Set คือ ข้อมูล + Index ที่ถูกเรียกใช้งานบ่อยๆ
-**SQL / Document DB (MongoDB):** เน้นการเก็บ Working Set ไว้ใน RAM เพื่อความเร็ว
-** ปัญหา:** เมื่อ Working Set > RAM ระบบจะเกิด **"Disk Thrashing"**(สลับข้อมูล RAM-Disk) ทำให้ Latency พุ่งสูงทันที

### 2. บทเรียนจาก Discord (MongoDB -> Cassandra)
Discord เคยประสบปัญหานี้เมื่อถึง 100 ล้านข้อความ:
-**MongoDB:** มีปัญหาเรื่องการจัดการหน่วยความจำและการทำ Sharding ที่ซับซ้อนในยุคนั้น
-** การตัดสินใจ:** ย้ายไป **Cassandra ** เพราะมันถูกออกแบบมาให้จัดการข้อมูลระดับ"Trillions" (ล้านล้าน) ได้โดยไม่ต้องเก็บ Index ทั้งหมดไว้ใน RAM (ใช้ LSM-Tree แทน)

### ตารางเปรียบเทียบเชิงลึก

| คุณสมบัติ | SQL (Relational) | NoSQL (Wide Column / KV) |
|:---|:---:|:---:|
|**Scaling **| Vertical (เน้นเครื่องเดียวแรงๆ) | Horizontal (เน้นเพิ่มเครื่องเล็กๆ) |
|**Consistency ⛓️ **| Strong (ACID) | Eventual (BASE) |
|**Index **| ต้องอยู่ใน RAM เพื่อให้เร็ว ⚡ | ออกแบบมาให้รับมือข้อมูลใหญ่กว่า RAM ได้ดี |
|** เหมาะสำหรับ **| ข้อมูลที่สัมพันธ์กัน, ยอดเงิน | ข้อความแชท, Log, ข้อมูลมหาศาล |

## ขยายความ (Extend)

### ยุทธศาสตร์ Senior: การเลือก Database ตาม Access Pattern
อย่าเลือก DB ตามความชอบ ให้เลือกตาม **"วิธีที่เราจะดึงข้อมูล"**:

**SQL:** ถ้าคุณต้องการ Query ที่หลากหลาย (เช่น"หายอดขายรวมแยกตามประเภทสินค้าและจังหวัด") SQL คือพระเจ้า
**NoSQL:** ถ้าคุณรู้ล่วงหน้าว่า 99% ของงานคือการ"ดึงข้อมูลตาม ID" (เช่น"เอาข้อความของ Channel นี้มาโชว์") NoSQL จะสเกลได้ดีกว่ามาก

### เทคนิค"NoSQL is for Specifics"
ใน NoSQL คุณต้องออกแบบตาราง ** ตามความต้องการของหน้า UI (Query-first design)** ไม่ใช่ตามความสัมพันธ์ของข้อมูล:
- ถ้าหน้า UI จะโชว์ข้อมูล 5 อย่างพร้อมกัน คุณอาจต้องเก็บข้อมูลทั้ง 5 อย่างไว้ในแถวเดียว (Denormalization) เพื่อให้ดึงจบในครั้งเดียว

<details>
<summary>ดูเฉลย (คลิกเพื่อเปิด)</summary>

ข้อมูลและ Index ที่ถูก ** เรียกใช้งานบ่อยๆ ** จนต้องอยู่ใน RAM เพื่อความรวดเร็ว
**CPU ว่างแต่ Latency สูง ** และค่า Disk Read/Write (I/O Wait) พุ่งสูงผิดปกติ
เพราะ SQL มีความสัมพันธ์ของข้อมูลที่ซับซ้อน (Joins, ACID) การแยกข้อมูลไปอยู่คนละเครื่องทำให้การทำ Transaction และ Join ข้ามเครื่องนั้น ** ช้าและซับซ้อนมาก **
